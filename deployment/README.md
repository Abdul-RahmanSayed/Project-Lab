# Local Deployment Preparation

Approved for local work after the [Slice 5A proposal](../docs/SLICE_5_DEPLOYMENT_PROPOSAL.md).
See [Slice 5B results](../docs/SLICE_5_LOCAL_PREPARATION_RESULTS.md) for measured evidence
and unperformed checks. Nothing in these files creates accounts or deploys a service.
Do not publish an archive/image, change GitHub visibility/Pages settings, provision
Render or edit the portfolio without the relevant approval.

## Files and Ownership

- `release.py`: standard-library streaming archive writer, exact-byte installer and
  build-only public-asset downloader. Reuses existing release/query validation.
- `release.lock.json`: reviewed archive/file sizes, hashes and selected release ID.
  Changing it is a release review, not an automatic data refresh.
- `serve.py`: existing API app factory with deployment environment validation,
  pinned-file checks, a single worker and the existing resource limits.
- `Dockerfile`: candidate Linux/amd64 build and non-root runtime. The database is
  baked into the image; no request/startup downloads or runtime preparation.
- `build-tools.lock.txt`: hash-pinned builder wheels; pip/setuptools are removed
  from the installed venv/base interpreter in the final serving filesystem.
- `input/release.tar.gz`: optional ignored local archive, never a Git source file.
- `preview.py`: loopback-only HTTPS static test server, with no API proxy.

The Docker context is explicitly allowlisted in the root `.dockerignore`. It
excludes Git metadata, source data, virtual environments, test certificates,
frontend files and unrelated generated output. The final image copies only the
installed Python environment, checked release and deployment lock, not a second
copy of the compressed archive. The October 21 Docker Desktop/WSL2 follow-up built
and checked this image under local Linux constraints; see [measured results](../docs/SLICE_5_LINUX_RESULTS.md).
This does not accept public-runtime security, a public-source rebuild or hosted behavior.

## Package and Check the Existing Release

From the Project Lab root with the existing API environment. Use a new output path
on each run; packaging/extraction refuse to overwrite an existing output directory.

```powershell
$releaseDir = 'generated/backend/release/18446003726ef6cb89bbb5cd07a265e8cf9fb3e4585fe5774ed4f6fd18454194'
$releaseId = 'fda-release-sha256:18446003726ef6cb89bbb5cd07a265e8cf9fb3e4585fe5774ed4f6fd18454194'
.\.venv-api\Scripts\python.exe -B -m deployment.release pack --release-directory $releaseDir --release-id $releaseId --output-directory generated/deployment/repack-1
.\.venv-api\Scripts\python.exe -B -m deployment.release extract --archive generated/deployment/repack-1/fda-18446003726ef6cb89bbb5cd07a265e8cf9fb3e4585fe5774ed4f6fd18454194.tar.gz --lock deployment/release.lock.json --destination generated/deployment/unpacked-1
```

The candidate lock generated by `pack` should agree structurally with the reviewed
lock. Archive headers have fixed names/order, zero timestamps/owners and read-only
file modes. Same local-runtime repacks were byte-identical; other compression/runtime
versions are not promised identical output. Do not replace the pin merely because
a repack differs. Install the already-reviewed archive or investigate the difference.

Extraction checks the compressed size/hash before creating output, streams only
the five exact approved regular files, rejects extra/duplicate/missing/path/link
members, checks each size/hash, and runs existing release/query validation. It
never uses `extractall`. The fresh destination inherits normal parent permissions,
then files are marked read-only. This avoids copying the original private Windows
temporary-directory ACL; it does not change the pinned builder or provide tamperproof
storage against an administrator. SQLite itself still uses read-only connections.

## Candidate Container Build

These commands require a working local Linux container engine. Abdul installed
Docker Desktop/WSL2, and the candidate build subsequently passed locally. Do not
install/enable additional runtimes or run a hosted build under the local approval.

For a local build without publishing anything, copy the reviewed archive to
`deployment/input/release.tar.gz` and, from the repository root, run:

```powershell
docker build --platform linux/amd64 --file deployment/Dockerfile --tag project-lab-api:local .
docker run --rm --publish 127.0.0.1:8768:10000 project-lab-api:local
```

Check `http://127.0.0.1:8768/readyz` and the documented overview/report cases. A later
Render build can supply `--build-arg FDA_RELEASE_URL=<approved-fixed-asset-url>`
instead of the ignored local archive. `fetch` only accepts the reviewed repository's
HTTPS `/releases/download/<fixed-tag>/<pinned-filename>` URL and approved HTTPS
GitHub asset redirects; it rejects `latest`, query credentials, wrong hosts and
oversized downloads. There is no real published asset to fetch in this phase.

The refreshed Python 3.14.8/Bookworm image is pinned to the actual Linux/amd64 digest
read from Docker Hub. It contains OpenSSL 3.0.22; SQLite remains the Bookworm build.
Builder pip 26.2.2/setuptools 84.2.1 wheels are hash-pinned. Both installed
interpreters in the final image have no importable pip/setuptools. The API's root
build metadata uses the refreshed setuptools pin; serving dependencies and all
release/data/policy/query pins remain unchanged. See the [refresh results](../docs/SLICE_5_RUNTIME_REFRESH_RESULTS.md).
This is not a full native-library security clearance or hosted acceptance.
Reconcile future runtime updates with existing pins; do not change policies or
regenerate the dataset silently. [Docker pinning guidance](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions).

### Repeat the Bounded Linux Check

After building the image, use a new output directory and an unoccupied loopback
port. The existing independent Python oracle must already be available locally:

```powershell
.\.venv-api\Scripts\python.exe -B tests/check_container.py --image project-lab-api:local --output-directory generated/deployment/linux-rerun-1
```

This creates only a temporary local container, capped at 0.1 CPU and 512,000,000
bytes/no swap, with read-only root/release files and non-root identity. It checks
eleven overview fixtures, bounded report pages/details, ten five-client default
waves and small repeated/mixed uncached batches, overload, resources and same-image
restart. It removes only its own container in cleanup; no publication or account
operation occurs. See the results for the deliberate pagination/sample limits.
The current harness also checks installed source bytes, OS/runtime versions and
packaging-tool absence in both Python environments. `tests/container_regressions.py`
runs the existing API suite inside this installed image with only the test module
and its three pinned pure-Python test wheels mounted read-only. It uses disposable
data copies for fault injection, not the original serving release; its method
and evidence boundaries are recorded in the refresh results.

Runtime settings:

- `FDA_RELEASE_DIRECTORY`: the installed five-file release directory.
- `FDA_RELEASE_ID`: optional cross-check; if provided it must match the lock.
- `FDA_ALLOWED_ORIGINS`: exact canonical HTTPS origins, comma-separated, no path,
  credentials, wildcard or trailing slash. Omit an explicit default `:443` port.
- `PORT`: 1-65535; defaults to 10000.

`serve` binds `0.0.0.0` for a container, one worker, connection/task limit 64,
five SQL jobs, no application pending queue and the unchanged 30-second SQL budget.
Access logs containing query strings are disabled. Configure the provider's health
check as `/readyz`, not `/healthz`. The old `backend.run` loopback runner is unchanged.
No CORS rule is authentication, a firewall or a guarantee against quota exhaustion.

## Frontend Origin and Project Path

`VITE_FDA_API_ORIGIN` is a trusted build-time public address, never a secret or a
visitor-selected URL. It accepts only a plain HTTPS origin. Queries omit browser
credentials; raw product text still travels through `URLSearchParams` unchanged.

```powershell
# Example only, after the actual API URL is approved and exists.
$env:VITE_FDA_API_ORIGIN = 'https://YOUR-APPROVED-SERVICE.onrender.com'
npm.cmd --prefix web run build:deployment
```

The dedicated deployment mode refuses an empty or invalid origin. It emits the
site under ignored `generated/deployment/site/Project-Lab`, separate from the normal
`web/dist` preview. Relative assets and hash routes work under `/Project-Lab/`.
`npm.cmd --prefix web run build` with no origin retains the local Vite proxy.
Environment values are baked into the frontend, not picked up later at runtime.
[Vite environment guidance](https://vite.dev/guide/env-and-mode).

Keep the static default/metadata/contracts paired with the same checked API release.
The browser retains the existing version/filter checks, response limits, cancellation,
saved labels, three bounded connection attempts and manual Retry. No keep-awake or
new caching/retry framework was added.

## Local Verification

```powershell
.\.venv-api\Scripts\python.exe -B tests/test_deployment.py --release-directory $releaseDir --output generated/deployment/unit-results.json
.\.venv-api\Scripts\python.exe -B -m backend.test_api --release-directory generated/deployment/unpacked --release-id $releaseId --output generated/deployment/api-results.json
npm.cmd --prefix web test
```

The separate HTTPS suite requires the reviewed archive already extracted at
`generated/deployment/unpacked`, and an isolated local wheel installation:

```powershell
.\.venv-api\Scripts\python.exe -m pip wheel --no-index --disable-pip-version-check --no-cache-dir --no-deps --no-build-isolation --wheel-dir generated/deployment/wheel .
.\.venv-api\Scripts\python.exe -m pip install --no-index --disable-pip-version-check --no-cache-dir --no-deps --target generated/deployment/installed generated/deployment/wheel/project_lab_api-0.1.0-py3-none-any.whl
New-Item -ItemType Directory -Path generated/deployment/tls -Force
& 'C:\Program Files\Git\usr\bin\openssl.exe' req -x509 -newkey rsa:2048 -nodes -keyout generated/deployment/tls/key.pem -out generated/deployment/tls/cert.pem -days 2 -subj '/CN=localhost' -addext 'subjectAltName=IP:127.0.0.1,DNS:localhost'
$env:VITE_FDA_API_ORIGIN = 'https://127.0.0.1:8767'
npm.cmd --prefix web run build:deployment
npm.cmd --prefix web run test:deployment
```

Use a fresh isolated installation directory for a new wheel, or deliberately
refresh that test installation; do not assume an old `pip --target` install was
replaced. Initial environment dependencies/build tools must already be installed.
Git's bundled OpenSSL path is specific to this Windows machine; use an available
OpenSSL elsewhere. No certificate is installed in an OS/browser trust store.

The suite refuses occupied ports, starts only its own loopback servers on 4174/8767,
and stops them afterward. Its API process uses Python isolated mode and the installed
wheel, not the checkout. Its HTTPS static server has no API proxy. Only the dedicated
test config bypasses certificate verification for the short-lived self-signed local
certificate; normal/hosted verification must not use that bypass. This is real local
TLS/CORS/outage/restart behavior, not public certificate, Render wake-up or provider
rollback evidence. No production control endpoint was introduced for the tests.

All archives, databases, wheels, certificates/private test keys, built output and
test evidence remain ignored. Do not stage them. The small deployment checksum lock
and source/config/tests are tracked candidates. FDA source, data semantics, the
portfolio, public services and Git history are unchanged.
